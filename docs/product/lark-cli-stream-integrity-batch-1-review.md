# 飞书 CLI 事件流完整性第一批独立复评

状态：**有条件通过本地适配器加固，不通过 live 切换或可靠投递声明**；2026-10-12。复评对象：[第一批计划](lark-cli-stream-integrity-batch-1.md)。

当前实现的主要缺口并非换一套飞书接入技术，而是既有 `lark-cli` subprocess 的生命周期与事件 journal 边界：`src/lark/stream.ts` 的异步 `onEvent` 无等待，ready 后失败观察不完整，超时退出可能 `SIGKILL`。`src/lark/service.ts` 的 `streams` Map 只防本 Service 重复启动，不能证明全局应用/订阅单 owner。因此本批修本地 stream 是必要但不充分的工作。

审查限制：

- 可改现有 adapter 源码与合成测试，必须保留 CLI 作为默认通道和现有公开 service API 兼容；不得修改现行 profile 开关或启动额外 live stream。
- 串行回调只能保证本地处理顺序；CLI 或飞书上游是否提供重放/确认未知，回调失败要暴露并失败关闭，不能宣称“零丢失”。
- 停机不得用 `SIGKILL`。若 graceful 超时，明确标记不确定的旧 consumer 存活，禁止自动重启形成双消费者；待人工/运行时核验后再处理。
- stderr 可能带错误信封或敏感数据；运行诊断只用结构化类别/退出码/事件键，不能把原文透传日志。
- `lark-event` Skill 关于本机 bus、ready marker 和进程停止的规则决定了上述门禁；跨应用/跨设备订阅身份仍需独立证据。

若要新增 CLI 预消费订阅、读取真实事件、修改现行进程或外部配置，本复评不放行，须先修计划并单独取得精确授权。

实现中复核：停机不仅等待 CLI 子进程退出，还必须等待在途 journal 回调，否则“已停”之后仍可写入。该竞态已纳入源码与离线测试；不扩大到真实运行切换。适配器健康可见不等于缺口自动补偿，后者仍单列验收。

实施后结论：完整 `npm run check` 与隔离 fake CLI 边界测试通过，保持“有条件通过本地适配器加固”的判定。未经真实 CLI 身份/订阅 scope、回放/补偿语义与单 owner 演练，完成度清单中的飞书订阅和无滴答门禁仍全部为 false。
